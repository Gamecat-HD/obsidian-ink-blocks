# Browser-runnable VLM / end-to-end OCR models for German handwriting in an Obsidian plugin (status: 2026-10-17)

Baseline for comparison: the current model, [naeyn/de-htr-web-v2](https://huggingface.co/naeyn/de-htr-web-v2), is a ResNet18 + 3xBiLSTM + CTC line recognizer with 10.06M params. The int8 file is 10.4 MB. It scores **8.01% CER / 32.3% WER** on 601 lines from 78 held-out writers of the ScaDS.AI German handwriting test set. Per-writer error is heavy-tailed: the median writer is about 6-8% CER, the hardest writers 30%+. It needs pre-cropped lines (Apache-2.0). Source: [model card](https://huggingface.co/naeyn/de-htr-web-v2).

Method note: I computed the download sizes below from the Hugging Face API file listings on 2026-10-17. Each figure is the sum of all `.onnx`/`.onnx_data` files carrying that dtype suffix. Repos often ship several decoder variants (`decoder_model`, `decoder_with_past`, `decoder_model_merged`), so these numbers are an **upper bound**. A real download, which needs only one encoder plus one merged decoder plus the embeddings, is typically about 50-70% of the figure. This is my inference; I did not check it file by file.

## 1. Candidates: which models have ONNX / transformers.js / WebLLM / wllama builds, plus size, license, German, benchmarks and demos

### Takeaway
The mid-2026 generation of compact OCR VLMs (≈0.9-1B params) now runs in transformers.js v4: **LightOnOCR-2-1B** and **GLM-OCR** are listed architectures with q4f16 ONNX builds of about 650-680 MB, and both declare German. Earlier small VLMs (Florence-2, SmolVLM, Granite-Docling, LFM2.5-VL-450M) are smaller at about 190-330 MB q4f16 and have working WebGPU demos, but none is trained or benchmarked for (German) handwriting. Several models have no browser build at all: DeepSeek-OCR, dots.ocr, olmOCR, Nanonets-OCR2, GOT-OCR, MiniCPM-V and Chandra. WebLLM's only VLM is Phi-3.5-vision (4.2B).

### Cited Findings

**Runtimes**
- transformers.js latest on npm is **4.3.1** (2026-10-06). 4.0.0 shipped 2026-03-30, 4.3.0 on 2026-09-16 ([npm registry](https://www.npmjs.com/package/@huggingface/transformers)). The v4 announcement is dated 2026-02-09 and introduced a new WebGPU runtime rewritten in C++ with the ONNX Runtime team. WebGPU models now also run in Node/Bun/Deno ([HF blog v4](https://huggingface.co/blog/transformersjs-v4)).

- Encoder-decoder models such as Florence-2 are "extremely sensitive to quantization settings", so transformers.js lets you set dtypes per module ([HF blog v3](https://www.huggingface.co/blog/transformersjs-v3)).
- **WebLLM** (MLC) prebuilt list: the only vision model among 169 entries is `Phi-3.5-vision-instruct` (q4f16_1 / q4f32_1) ([web-llm config.ts](https://github.com/mlc-ai/web-llm/blob/main/src/config.ts)). - **wllama** (llama.cpp WASM): v3 wraps llama-server's `server-context`. "Models with a vision projector (mmproj) can now process image and audio inputs", and a multimodal demo is linked ([wllama v3 intro](https://unpkg.com/@wllama/wllama@3.6.1/guides/intro-v3.md)). The older 3.4.1 README lists WebGPU and image input, needs COOP/COEP headers for multithreading, and caps single files at 2 GB ([wllama README 3.4.1](https://cdn.jsdelivr.net/npm/@wllama/wllama@3.4.1/README.md)). Any GGUF VLM with an mmproj is therefore a candidate in principle, for example GLM-OCR has [ggml-org/GLM-OCR-GGUF](https://huggingface.co/ggml-org/GLM-OCR-GGUF), and there are Surya-OCR-2 GGUF and Nanonets-OCR-s GGUF ([HF search](https://huggingface.co/models?search=ocr)).

### Inferences
- Realistic shortlist under ~700 MB with transformers.js support and declared German: **GLM-OCR** (MIT, about 650 MB, best handwriting fidelity among the compact models per WildHandBench PDE), **LightOnOCR-2-1B** (Apache-2.0, about 680 MB, German in its training languages, no handwriting evidence), and **LFM2.5-VL-450M** (about 320 MB, German, but a general VLM with OCRBench 684 and no handwriting data). After de-duplicating decoder variants, real downloads are likely about 400-500 MB for the 0.9-1B OCR models.
- Florence-2, SmolVLM, SmolDocling and Granite-Docling are small and have demos, but they are English/printed-document models. They are very unlikely to beat an 8% CER German line model on handwriting.
- Qwen3-VL-2B (about 1.4 GB, upper bound) is the most plausible "general VLM with good handwriting" in a browser, but it sits at the upper limit of acceptable download size.
- PP-OCRv6 small/medium is an additional non-VLM option that supports German and runs in the browser. Its handwriting numbers are only for Chinese and English handwriting.

### Gaps
- I found **no German-handwriting benchmark (CER) for any of these small VLMs.** WildHandBench covers zh/en only, OmniHandwritingOCR en/zh only, and PP-OCRv6 handwriting only CN/EN. On German historical data, the arXiv HTR benchmark ([Crosilla et al.](https://arxiv.org/abs/2503.15195)) reportedly found that LLMs are beaten by Transkribus on READ2016, according to a search snippet I could not verify in the full text.
- I found no IAM CER for Florence-2, SmolVLM, Granite-Docling, LFM2.5-VL, LightOnOCR-2 or GLM-OCR.
- No measured browser memory (RAM/VRAM) figures exist for any of these models. TeleOCR's card only says memory grows with image size: about 120 MB per attention score buffer at 1036x1036.
- License of the onnx-community Qwen3-VL-2B and Qwen2.5-VL-3B ONNX repos is not set; upstream Qwen3-VL-2B is Apache-2.0.

## 2. Handwriting ability (especially non-English) and hallucination risk: VLMs vs CTC

### Takeaway
2026 handwriting benchmarks show that compact OCR VLMs (0.9-1.2B) are weak on handwriting, with English-handwriting CER around 40-90% on hard sets. Only large general VLMs (Qwen3-VL-8B and above) are clearly good. All VLMs make "prior-driven" errors, meaning fluent but visually unsupported text. CTC models, in contrast, err visually rather than fabricating words, and are reported to hallucinate less. GLM-OCR and PaddleOCR-VL have the lowest prior-driven error share among the models tested.

### Cited Findings
- **WildHandBench** (Baidu, 2026-08-24; 500 handwritten docs in zh/en; 18 models): "models that exceed 90% on OmniDocBench … drop to 71.85% at best on WildHandBench". "OCR-focused models … fall behind general VLMs on wild handwriting. The top six models … are all general-purpose" ([arXiv 2608.22959](https://arxiv.org/abs/2608.22959)).
- WildHandBench text edit distance (lower is better) for the compact models: GLM-OCR (0.9B) 54.20, PaddleOCR-VL-1.6 (0.9B) 41.52, HunyuanOCR (1B) 38.50, MinerU2.5 (1.2B) 83.80, MinerU2.5-Pro 59.80, FireRed-OCR (2B) 49.00, Dots.ocr (3B) 56.68, DeepSeek-OCR2 91.70. Large models: Gemini 3.1 Pro 24.32, Kimi-K3 26.07, Qwen3-VL-235B 34.30; human baseline 30.08 ([arXiv 2608.22959](https://arxiv.org/abs/2608.22959)).
- WildHandBench Prior-Driven Error (PDE) metric: across functional models, PDE ranges from 63% to 79%. "powerful language priors act as a double-edged sword: they boost accuracy by correctly inferring ambiguous characters, but when errors do occur, those errors are disproportionately prior-driven … confidently generate plausible alternatives rather than fail silently". The lowest-PDE models are "GLM-OCR, PaddleOCR-VL", whose errors are more often visual confusions. Formula errors are 87-98% prior-driven across all models. Human PDE is 49.27% overall ([arXiv 2608.22959](https://arxiv.org/abs/2608.22959)).
- **OmniHandwritingOCR** (ECNU, CIKM '26, 2026-08-19). English handwriting text (IAM-line + GNHK) CER: Qwen3-VL-8B 16.44%, Qwen2.5-VL-72B 16.01%, Nanonets-OCR2-3B 19.41%, GPT-4o 20.05%, MonkeyOCR-pro-1.2B 23.64%, Gemma-3-27B 26.12%, DeepSeek-OCR 39.83%, GOT-OCR2 43.17%, **PaddleOCR-VL 47.48%**, MinerU2.5-1.2B 93.43%. The paper observes that Qwen2.5-VL-72B and InternVL3-78B "incorrectly produce corrected but visually unsupported transcriptions". Caveat: the dataset was challenge-filtered using Qwen2.5-VL-72B, which inflates the error rates ([arXiv 2608.18586](https://arxiv.org/abs/2608.18586)).
- **PP-OCRv6** (Baidu, 2026-06), a CTC+NRTR recognizer: on a curated hallucination benchmark, PP-OCRv6_medium scores 93.2% accuracy vs 80.6% (Qwen3-VL-235B), 78.0% (GPT-5.5), 85.0% (Kimi-K2.6) and 72.6% (MiniMax-M3). The authors explain: "CTC+NRTR decoding architecture produces outputs grounded in visual features, whereas VLMs' auto-regressive generation may produce plausible but non-existent text." This is a vendor in-house benchmark ([arXiv 2606.13108](https://arxiv.org/abs/2606.13108)).
- The same paper's in-house handwritten **English** accuracy: Qwen3-VL-235B 73.2, Gemini-3.1-Pro 73.0, PP-OCRv6_medium 67.8, PP-OCRv6_small 61.1. On this column large VLMs beat the CTC model. On handwritten Chinese, PP-OCRv6_medium has 62.1 vs GPT-5.5 at 19.2 ([arXiv 2606.13108](https://arxiv.org/abs/2606.13108)).
- Crosilla, Klic, Colavizza (2025, arXiv 2503.15195, datasets in English, French, German and Italian) find that LLMs show "limited ability to autonomously correct errors in zero-shot transcriptions", and that Claude 3.5 Sonnet beat the open-source models ([arXiv abs](https://arxiv.org/abs/2503.15195)). [2025]
- A vendor blog argues that VLMs resolve ambiguous handwriting toward the most probable completion, citing a "1" read as "7". This is opinion, not measured data ([Nutrient](https://www.nutrient.io/blog/handwriting-recognition-ocr-vlm/)).
- Doctor-handwriting informal test: GLM-OCR CER 0.328 vs 0.477 for PP-OCRv5. This is a single blog post ([DEV](https://dev.to/kaniel_outis/how-well-can-ocr-read-doctor-handwriting-in-2026-54hn)).

### Inferences
- On short German handwritten lines with IT strings (IPv6, subnet masks, hex), language priors work against you. The model "knows" German words and common formats, so it may normalize `fe80::1a2b` or `255.255.255.0`-like strings, or "fix" spelling. WildHandBench's finding that formula/LaTeX errors are 87-98% prior-driven is the closest analogue to structured technical strings.
- None of the compact VLMs has demonstrated a sub-10% CER on any handwriting set. On the hard English sets their CER is several times de-htr-web-v2's 8% on German. It is therefore unlikely that a ≤1B browser VLM beats the existing CTC model on German handwriting without fine-tuning. The main exception may be general-purpose Qwen3-VL (2B/4B), whose 8B sibling is strong. This is extrapolation, not measured.
- VLMs could add value on **printed or mixed content** (screenshots, printed handouts, typed text inside ink blocks) and on page-level input without line segmentation.

### Gaps
- There is no published CER for any browser-sized VLM on German handwriting (ScaDS.AI, fhswf/german_handwriting, READ2016). A local test on the plugin's own data is the only way to know.
- Hallucination rates for small (≤2B) VLMs specifically are not reported. The PP-OCRv6 hallucination table covers only very large VLMs.

## 3. WebGPU availability in Electron (Linux/AMD/Mesa, Windows) and browser performance

### Takeaway
Electron 43 ships Chromium 150, so WebGPU itself is present. On Linux, a hardware adapter needs Chromium's **Vulkan feature** enabled. `--enable-unsafe-webgpu` alone gives only SwiftShader, a CPU renderer. Those switches have to be set by the host app (Obsidian) at startup, which a plugin cannot do. On Windows, Chromium's WebGPU defaults to Dawn/D3D12. Expect WebGPU to work there by default if Obsidian's origin is a secure context and the GPU isn't blocklisted. WebGPU decodes about 40x faster than WASM for small LMs.

### Cited Findings
- Electron 43 upgrades Chromium 148.0.7778.96 → **150.0.7871.46**, Node 24.17.0, V8 15.0 ([Electron 43 blog](https://electronjs.org/blog/electron-43-0)).
- Shift editor PR #560 (Electron app; opened 2026-10-08, merged 2026-10-09) was tested on Ubuntu 24.04 with GNOME Wayland, an AMD Renoir GPU and Mesa 25.2. Results: with no switches, `navigator.gpu.requestAdapter()` returns null; with `--enable-unsafe-webgpu` alone it gets SwiftShader; with the Chromium **`Vulkan`** feature enabled it gets the hardware adapter (`amd rdna-2`). The PR therefore enables Vulkan at startup on Linux ([shift PR #560](https://github.com/shift-editor/shift/pull/560)).
- A Figma/Electron probe on Linux/AMD reports `--ozone-platform=x11 --ignore-gpu-blocklist --enable-unsafe-webgpu` as its working recipe ([gist](https://gist.github.com/arximus88/f8d93ae1568a5c49e4206250f323b178), per search snippet). Vulkan ANGLE is reported incompatible with Wayland in Flatpak Chrome ([gist](https://gist.github.com/davidar/2bbc7399f3aa2523efb3637dad2b0d50), per search snippet). These conflict with Shift's result, which worked on Wayland GNOME with Vulkan alone.
- Older Electron issue #41763: null WebGPU adapter on Linux; a maintainer said WebGPU is enabled by default, and commenters reported Electron ignored Vulkan switches. This is dated (2024) ([electron#41763](https://github.com/electron/electron/issues/41763)).
- Chrome: WebGPU is available by default on ChromeOS/macOS/Windows from Chrome 113. It requires a **secure context** and can be disabled by GPU blocklisting ([Chrome WebGPU troubleshooting](https://developer.chrome.com/docs/web-platform/webgpu/troubleshooting-tips)). On Windows, Chrome's WebGPU uses Dawn with D3D12 as the default backend, not ANGLE ([NVIDIA forum](https://forums.developer.nvidia.com/t/failed-to-collect-gpu-trace-with-webgpu-on-chrome/296805), per search snippet).
- Performance data points:
  - SmolLM2-360M in-browser: WebGPU median **62.9 tok/s** vs **1.6 tok/s** on WASM ([DEV](https://dev.to/mattbusel/run-an-llm-in-the-browser-webgpu-did-63-tokenss-wasm-did-16-24ob)).
  - SmolVLM-256M: up to 80 decode tok/s via WebGPU on an M4 Max ([SmolVLM paper](https://arxiv.org/abs/2504.05299)).
  - TeleOCR 1.4B q4f16 on an AMD Radeon 8060S iGPU (Linux/Vulkan, Chrome 154): TTFT 0.13-2.1 s, 65-90 tok/s decode; fp16 29-33 tok/s. CPU (Python ONNX Runtime, not browser WASM): 57 tok/s ([TeleOCR-ONNX](https://huggingface.co/stefanj0/TeleOCR-ONNX)).
  - Throughput varies 27-67 tok/s on the same laptop depending on GPU contention ([Pinggy](https://pinggy.io/blog/run_llm_in_browser_webgpu/)).
- PaddleOCR-VL in-browser app offers WebGPU and a CPU/WASM path; it recommends a "capable GPU with WebGPU support" ([chunks.md](https://chunks.md/paddleocr-vl-1-6-online)).

### Inferences
- For an Obsidian plugin on the user's CachyOS/Hyprland/AMD machine, WebGPU will most likely **not** give a hardware adapter unless Obsidian is launched with Vulkan enabled, for example `--enable-features=Vulkan` in `~/.config/obsidian-flags.conf` or the .desktop file. That is a per-user setup step, not something the plugin can toggle. The plugin should probe `requestAdapter()` and check `adapter.info` to detect SwiftShader. If it finds SwiftShader, it should fall back to WASM.
- On WASM, a 0.9-1B VLM decodes at roughly 1-5 tok/s (extrapolated from 1.6 tok/s for a 360M model with WebGPU off). A 30-token line would take about 10-30 s plus vision-encoder prefill, which is acceptable only as an idle background job with very few lines. Page-level OCR would take minutes.
- Windows (HP laptop): WebGPU via D3D12 is likely to work out of the box in Obsidian.

### Gaps
- I did not verify whether Obsidian's `app://` origin counts as a secure context for WebGPU, or whether Obsidian ships any GPU flags.
- I found no measured transformers.js numbers for GLM-OCR or LightOnOCR in a browser, and no WASM VLM numbers at all.
- I found no Electron 43-specific WebGPU-on-Linux regression or fix notes.

## 4. Could a small VLM be used only as a second-pass verifier/corrector over CTC output?

### Takeaway
Yes, but only in a constrained role. The evidence says VLM errors are mostly fluent, prior-driven substitutions, and that LLMs are poor at autonomously correcting HTR output. A safe design keeps the CTC output as the primary text. It uses the VLM to **add** alternative readings to the search index, or to **score** CTC candidates, rather than letting the VLM freely rewrite the text.

### Cited Findings
- LLMs show "limited ability to autonomously correct errors in zero-shot transcriptions" ([Crosilla et al. 2025](https://arxiv.org/abs/2503.15195)).
- Strong language priors "boost accuracy by correctly inferring ambiguous characters, but when errors do occur, those errors are disproportionately prior-driven", and the model generates "plausible alternatives rather than fail silently" ([WildHandBench](https://arxiv.org/abs/2608.22959)).
- VLMs "correct" spelling and grammar that CTC models reproduce faithfully. The PP-OCRv6 qualitative examples show deliberate misspellings preserved by CTC and changed by GPT-5.5 / Qwen3-VL-235B ([PP-OCRv6](https://arxiv.org/abs/2606.13108), per search summary; the hallucination table is quoted in section 2).
- transformers.js exposes models through `AutoModelForVision2Seq`/`generate`. Per-module dtype control is available, which matters for encoder-decoder sensitivity ([HF blog v3](https://www.huggingface.co/blog/transformersjs-v3)).

### Inferences
These are design ideas, not sourced.
- **Search-index union:** store the CTC text plus the VLM text (or only the tokens where they differ) in the hidden search field. Recall goes up, and a VLM hallucination only adds a spurious search hit instead of corrupting visible text. This fits the "searchable field" use case best.
- **Gated re-reading:** run the VLM only on lines where the CTC per-character posteriors are low. Accept the VLM output only if its edit distance to the CTC output is small (for example ≤20%), and never for tokens matching IP/hex/numeric patterns.
- **Candidate scoring instead of generation:** take CTC beam/N-best outputs and score each with the VLM's teacher-forced log-likelihood given the image. This needs a forward pass with logits, which ONNX/transformers.js allows. The VLM then cannot introduce text that the CTC lattice didn't propose.
- Cost: a 300-700 MB VLM used as a verifier on a few uncertain lines per idle period is feasible on WebGPU (TTFT under about 2 s for a 1.4B model on an AMD iGPU per TeleOCR) and borderline on WASM.

### Gaps
- I found no published study of a "CTC + small VLM verifier" pipeline for handwriting, nor any measurement of how often small VLMs flip a correct CTC line to an incorrect one.

## 5. Chrome built-in AI (Prompt API / Gemini Nano, multimodal) in Electron

### Takeaway
No. Gemini Nano is not part of Electron. Electron implemented an RFC, landing in **v45**, that lets an app route Prompt API calls to a **local model of the app's choice** via a main-process handler. The model is not bundled, image input is not addressed, and Obsidian on Electron 43 predates it. A plugin cannot install a main-process handler anyway.

### Cited Findings
- Electron RFC 0014 "AI Prompt API" has status "Completed", landed in **Electron v45.0.0** (start date 2025-04-09). Apps register `Session.registerLocalAIHandler` / a new `localAIHandler` module in a utility process and proxy Built-in AI calls to "a local LLM implementation of their choice". No Gemini Nano is bundled; a default implementation is only listed as a future possibility. Multimodal input is not covered ([electron/rfcs 0014](https://github.com/electron/rfcs/blob/main/text/0014-ai-prompt-api.md)).
- In Chrome, the Prompt API downloads Gemini Nano separately on first use. Requirements: at least 22 GB free storage and a GPU with more than 4 GB VRAM, or 16 GB RAM with 4+ cores ([Chrome Prompt API docs](https://developer.chrome.com/docs/ai/prompt-api)).
- Multimodal (image/audio) input arrived in Chrome 138 for the Early Preview Program ([Chrome I/O 25 update](https://developer.chrome.com/blog/ai-api-updates-io25)). Localhost testing uses the flag `#prompt-api-for-gemini-nano-multimodal-input` ([Chrome docs](https://developer.chrome.com/docs/ai/prompt-api)). MDN documents `expectedInputs` for image/audio ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Prompt_API/Multimodal)).
- Separate route: Microsoft's `windows-ai-electron` is an experimental native addon exposing Windows AI Foundry APIs to Electron. It is Windows-only and its `LanguageModel` differs from the web API ([microsoft/windows-ai-electron](https://github.com/microsoft/windows-ai-electron)).

### Inferences
- Even after Obsidian moves to Electron ≥45, the Prompt API would only exist if Obsidian itself registered a handler. Gemini Nano's 22 GB disk / 4 GB VRAM requirements are far beyond the 1 GB budget anyway. Chrome built-in AI is not a viable path for this plugin.
- `windows-ai-electron` would need a native module and Windows Copilot+ hardware; it is not usable from an Obsidian plugin on Linux.

### Gaps
- I could not confirm whether multimodal Prompt API input is enabled by default in Chrome stable as of October 2026. The most recent official material I found (2025) describes it as early preview behind a flag.
- The exact Electron 45 release date and whether Obsidian has adopted Electron 45 are not verified.
